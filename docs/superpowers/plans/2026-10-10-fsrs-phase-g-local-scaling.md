# FSRS Phase G: Measured Local Scaling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Measure local growth across the full extension path, improve only demonstrated bottlenecks, and preserve identical product results and durable recovery behavior.

**Architecture:** A deterministic fixture module under `src/testing` prepares disposable SQLite databases outside timed operations. A CLI/Vitest runner supplies repeatable query and storage baselines. The existing dashboard-only `/dev/smoke` service reports packaged Chrome timings and storage costs through existing trusted handlers; it does not load fixtures or invoke sync or AI. Measurements guide changes within Practice, Analytics, Backup, and Platform owners, with full-reference output parity.

**Tech Stack:** Node 24.20.0, npm 11.19.0, Chrome MV3/WXT, SQLite WASM, Drizzle, ts-fsrs 5.4.0, Zod, Vitest, Chrome storage APIs.

**Approved design:** [FSRS remediation design](../specs/2026-10-03-fsrs-remediation-design.md), especially “Measured local scaling: priority 8”; [master roadmap](./2026-10-03-fsrs-remediation.md), Phase G. `origin/main` was verified at `c4ce5d9568131e09b3ee3c9586fe76f7283cb32e` (Phase F, PR #208) before branching. Phase F's human smoke and visual proof remain pending in its handoff; merge status does not close that gap.

## Measurement contract and decisions

- Datasets have seed `20261010`: **standard** 250 problems/5,000 reviews; **stress** 2,500/50,000; **single-card** 10,000 events on one card. The generator validates exact counts, FK integrity, sequence/revision consistency, card/evidence/log parsing, Practice storage and a full backup preflight. Include realistic notes/log lengths, day gaps, equal timestamps with distinct application order, corrections, captured/legacy-derived/unknown provenance, 75%/90% profiles, suspension, premium exclusions and track associations. Trusted evidence uses the real FSRS codecs and matching pre-card/profile/log; unknown evidence has no invented profile. Load only disposable databases; never replace the normal Chrome profile or run live sync/AI.
- Fixture construction, opening and migration are outside warm-operation timers. “Warm” means the same opened worker and SQLite handle; “cold reopen” means stop/restart the worker and reopen the **same published fixture snapshot**, not an empty fresh profile. Each named operation has 3 untimed warmups and 20 timed warm samples on standard/single-card where feasible, 10 on stress; cold open/reopen has 5 independently restarted samples where automation permits. Record every raw sample, p50 (nearest rank), p95 (nearest rank), failure/timeout and exact sample count. Do not report p95 for fewer than 5 successes. Freeze clock, operation input and target card per comparison; mutations use restored identical fixture copies so growth does not contaminate later samples. Byte-for-byte fixture determinism applies within the pinned toolchain/SQLite build and canonical insertion order.
- Time the **dashboard/runtime request through durable acknowledgement** for Save, Update and identical-command Retry; separately report transaction/query, shared-gate wait, FSRS/model, SQLite export, base64 encoding and `chrome.storage.local.set` when instrumentation can isolate them without material overhead. Measure Queue, Practice details/recent rows, Analytics 30/90/All, Phase F Submit/Update preview (alone and concurrent with Save), backup export/validation, restore, publication, worker restart and reopen. Contention belongs in end-to-end latency.
- Record commit, fixture seed and verified counts; OS/hardware/Chrome/extension build/dependency versions; cold/warm definitions; `performance.memory`/Chrome heap measurements when available and their limitations; SQLite/export/base64/backup byte counts; active and recovery copy sizes; `chrome.storage.local.getBytesInUse(null)` total, published quota and measured headroom. Never output database, key, token, snapshot, backup or review contents in benchmark reports. `QUOTA_BYTES` may be unavailable or differ by Chrome/permission; report the actual API and error instead of inferring capacity from raw SQLite size.
- Baseline-derived budget: preserve the complete raw baseline, then set each measured comparison's budget to its own baseline p50/p95 and measured noise band (two baseline runs). A production change is justified only by an attributable bottleneck accounting for at least 20% of end-to-end time, a reproducible failure/boundary, or a major memory/storage cost. Require a repeatable improvement outside the baseline noise band, no material regression in other measured operations, exact reference-output parity, and passing preservation/fault tests. No absolute latency or supported-capacity promise follows from these workloads. If the stress dataset reaches quota or cannot complete safely, record the reached row/byte boundary and unchanged last durable state; do not prune history or alter permissions.
- Installed Chrome evidence is separate from CLI/in-memory evidence. A production build and automated tests do not prove installed Chrome measurements. A local Chrome driver under `scripts/fsrs-scaling-chrome.mjs` launches the **packaged build** with a unique `/private/tmp` user-data directory, preflights the existing `@webext-core/messaging` wire protocol with `runtime.ping`, calls existing authorized dashboard messages from the dashboard origin for Save/Update/Retry/Queue/details/Analytics/backup, and records request-to-response samples outside the extension. A content-script driver on a real problem page measures F previews through its authorized sender; it is a separate reported channel and must remain pending if a valid problem page cannot be loaded. The driver restores a verified fixture snapshot between mutating samples, checks post-load counts/digest (taxonomy reconciliation may change imported rows), disables and verifies sync/AI before restore, forces `runLiveGenAi: false`, and stores sanitized raw JSON evidence under `docs/superpowers/evidence/`. After each restore it fetches fresh Practice generation/target/revision, then submits the same logical command; same-command Retry runs immediately after the accepted command on that fixture, before any reset. Its cold samples stop/restart the service worker while keeping the same published snapshot. The hidden `/dev/smoke` service shows an opt-in **read-only** capacity/storage report and read-operation samples, gated for database access; it does not pretend to collect mutation or content-script samples. It must distinguish its sequential health checks from separately timed endpoints. No fixture loader, permission or destructive control ships in the extension.

## Acceptance gate

Phase G is ready for PR review only when fixtures are reproducible and valid, every feasible named operation has raw packaged Chrome evidence (missing packaged operations remain unmet deliverables even if CLI measurements exist), all optimized outputs equal the full reference, fault/recovery/concurrency behavior is proven, validation and skipped commands are explicit, independent reviews are resolved, and the human engineer has supplied the required installed-extension happy/edge smoke and visual proof. A draft PR may exist while that final human gate is pending.

## Pre-implementation review

Independent SPEC and runtime reviews found that a read-only `/dev/smoke` report could not by itself measure real Save/Update/Retry, restore or content-script previews. The plan now assigns those timings to a disposable-profile packaged Chrome driver and keeps the smoke service read-only. The reviews also required post-restore digest verification, fresh generation tokens after each restore, paired same-command Retry, a messaging preflight, shared-gate reads, sync/AI isolation and honest pending status for unavailable packaged evidence. Both reviewers found no remaining blocking plan gap after these repairs. Implementation and its final independent reviews remain open.
