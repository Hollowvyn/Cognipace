# FSRS Phase H: Local Personalization Evaluation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Stop at each acceptance gate; a documented decision to retain defaults is a valid final result.

**Goal:** Determine whether an official, local FSRS optimizer can safely improve prospective CogniPace scheduling, and expose deliberate activation only if packaged runtime and held-out prediction evidence support it.

**Architecture:** Keep `src/lib/fsrs` as the sole optimizer and scheduler integration boundary. Practice owns a consistent, bounded history export and any active profile mutation; the dashboard owns an explicitly started, cancellable worker. Training runs after the shared database gate is released. Candidate comparison uses a chronological held-out split and never changes the incumbent until a separate guarded, durable activation.

**Tech stack:** Node 24.20.0, npm 11.19.0, lockfile WXT 0.21.3, Chrome MV3, SQLite WASM, Zod, Vitest, `ts-fsrs` 5.4.0, official `@open-spaced-repetition/binding` and `@open-spaced-repetition/binding-wasm32-wasi` 0.5.0. The pre-existing local `node_modules` currently resolves WXT 0.21.4, so run `rtk npm ci` before reproducible packaged measurements and record the resulting installed version.

---

**Approved design:** [FSRS remediation design](../specs/2026-10-03-fsrs-remediation-design.md), “Personalization: priority 7”; [A–H roadmap](./2026-10-03-fsrs-remediation.md), “H: personalization acceptance.” This plan implements the approved conditional pilot, not a new service or scheduler policy.

**Verified baseline:** This branch starts at `origin/main` merge `ef14c1a5` (Phase G, PR #209), rather than the older Phase E checkout. Node and npm match the pinned versions. The G standard packaged fixture used 9,776,228 of 10,485,760 Chrome local-storage bytes, leaving 709,532 bytes. Its optimized Analytics All p50 was about 1,165 ms. The 50,000-review packaged restore hit the runtime message-size limit before load; the one-card/10,000-event restore returned persistence-pending with tracked durable keys unchanged. These are measured boundaries of those fixtures and builds, not general limits. The sampled dashboard heap excludes service-worker heap and continuous peak memory. D/E/F/G PR bodies and handoffs still record human installed-extension smoke and visual proof as pending; merged status does not close those gates.

## Decision branches

1. **Official packaged path succeeds:** Continue with canonical history, worker evaluation, guarded activation, documentation and required proof.
2. **Packaged path or model compatibility fails within the authorized architecture:** Stop product implementation, remove spike code and dependencies, retain defaults, and publish a reproducible feasibility decision and A–H traceability record. Do not substitute a custom optimizer, remote service, extra Chrome permission, `unlimitedStorage`, or an unapproved cross-origin isolation change.
3. **Runtime works but one user-started run is inconclusive:** Report its coverage and uncertainty, keep the incumbent, and offer no activation for that run. Synthetic results validate the evaluator, not a person's benefit. If the pilot as a whole cannot make a trustworthy per-run decision, remove its UI and unused persistence and retain defaults.

## Task 1: Confirm the official package and isolate a packaged feasibility probe

- [ ] Record exact package tarball/version/license/API and scheduler version. Context7 resolves `/open-spaced-repetition/ts-fsrs` and the official binding documentation; the published binding 0.5.0 has a separate WASI asset. Its `FSRSBindingItem` represents one observation with preceding reviews, the first gap is zero, and `computeParameters` requires `enableShortTerm: false` for CogniPace's daily policy. The binding uses fsrs-rs 6.5.0 while the installed scheduler reports FSRS-6.0; 21 weights alone are insufficient compatibility proof.
- [ ] Add a **disposable**, source-controlled probe that bundles exact 0.5.0 WASM and worker assets using the published `initOptimizer({ wasm, worker })` pattern. Start it from the packaged dashboard, with current MV3 manifest and CSP first. Do not modify cross-origin isolation or permissions to make the probe pass. Record asset byte sizes, worker startup time, `crossOriginIsolated`, actual CSP/worker errors, thread count and termination. A build or Node-only run does not satisfy this gate.
- [ ] Feed only small synthetic items and call `computeParameters` with `enableShortTerm: false`, a fixed seed/training configuration where supported, progress callback, and cancellation. Measure wall time, main-thread responsiveness, worker count, dashboard and service-worker heap where measurable, and recovery after cancellation, dashboard navigation, worker termination and repeated runs. Record how heap was sampled and which peaks remain unknown.
- [ ] Validate an actual trained vector through `parseFsrsSchedulerProfile` and exact native reconstruction using the saved daily retention, empty steps, fuzz disabled and native maximum interval 180. Compare binding and `ts-fsrs` predictions on the **same** synthetic review histories and ratings; require numerical agreement under an explicitly recorded tolerance justified by f32 conversion. Any structural or semantic mismatch fails activation feasibility.
- [ ] Use `rtk npm run test -- src/lib/fsrs/optimizer/official-binding.test.ts`, `rtk npm run build`, `rtk npm run zip`, and `rtk proxy node scripts/fsrs-personalization-chrome.mjs --stage feasibility` on a unique disposable Chrome profile. Archive sanitized raw samples and build hash. If startup needs an isolation manifest change, report the failure and stop; that global change is outside this approved pilot.

**Gate 1:** Proceed only if the exact official binding starts and trains in packaged Chrome under the existing authorized manifest, the dashboard remains responsive, cancellation/closure releases workers, repeated runs do not accumulate resources, and actual trained weights reconstruct and predict compatibly. Otherwise execute the defaults-retained branch and complete Tasks 6–7 as a feasibility handoff.

## Task 2: Build a consistent, canonical history read without training under the database gate

- [ ] Write focused tests for one retained observation per `review_attempts` row joined to `practice_review_evidence`, with durable card ID, event ID, original reviewed time, application sequence, current correction revision, rating, sequence/evidence source and assessment policy/source. A corrected event replaces its old rating; command receipts and superseded acknowledgements add zero observations. Reset removes its card history; restore starts a new lifecycle generation without rewriting retained rows.
- [ ] Add a Practice-owned bounded projection, validated with Zod at the runtime boundary. Order each card by application sequence, not Analytics topic joins or wall time alone. Preserve equal timestamps with sequence order. Label and exclude ambiguous or invalid legacy evidence from the primary training cohort without changing stored history. Report total, usable, legacy, ambiguous, policy-changed and excluded counts.
- [ ] Add a durable monotonic Practice history mutation version, incremented atomically on Save, Update, per-problem reset and full replacement, with additive migration and backup/restore semantics. Pair it with the lifecycle generation and canonical content fingerprint. Existing generation tokens alone do not change on ordinary Save/Update. Check the version before and after bounded chunk transfer and again inside activation's short guarded transaction; discard a mixed or stale snapshot. Measure gate duration, chunk bytes, message copies and 5,000-review transfer cost against G's packaged fixture. Do not send a 50,000-review history in one runtime response or keep the gate held during training.
- [ ] Run focused Practice, runtime contract, backup/restore and integration tests and the packaged transfer driver. Require unchanged card, log, history, profile, receipt, raw due, track and progress digests after read-only export.

**Gate 2:** Proceed only with a consistent, bounded snapshot that stays within the measured installed-extension memory/message/storage limits and does not interrupt authoritative Save/Update for a long training run. Do not set a universal minimum attempt count; readiness depends on usable repeat histories and measurable evaluation coverage.

## Task 3: Define day-gap conversion and leakage-free evaluation

- [ ] Test the exact conversion from actual event instants to binding integer day gaps. Define the study-day calendar/time zone used, keep first gap zero, handle genuine same-day reviews as zero gap, keep tied times in application order, reject negative/nonfinite gaps, and report the lost sub-day timing precision. Keep the active daily policy's empty learning/relearning steps and disabled short term explicit.
- [ ] Use a global chronological cutoff; keep equal-time groups together and build each held-out observation only from its own card's preceding valid events. If a card contains an earlier ambiguous, invalid or policy-incompatible event, exclude all of its later observations from the primary cohort rather than silently skipping that event and fabricating a new state or gap. Train only on pre-cutoff observations. Evaluate candidate, defaults and incumbent on identical held-out repeat observations, identical rating definitions (`Again` is failure; `Hard`, `Good`, `Easy` are recall), and retained original times. Never score a candidate against a precomputed incumbent card state or include a held-out rating in its input state.
- [ ] Pre-register paired held-out log loss as the primary decision metric, calculated from the same `ts-fsrs` prediction path for all three profiles. Report the official binding's `logLoss` and `rmseBins` as diagnostics where supported, not as substitute cross-model metrics. Resample by independent card history for a 95% interval on candidate-minus-default and candidate-minus-incumbent mean paired loss; if independent histories are too few for a meaningful interval, mark the run inconclusive. Require both intervals entirely below zero for activation eligibility. Report eligible card/event counts, policy exclusions and coverage; no fixed universal raw-attempt threshold substitutes for this evidence. Falling training loss alone does not count as improvement.
- [ ] Test malformed/nonfinite/out-of-range weights and exact scheduler reconstruction; include a synthetic outcome where the candidate loses, one where coverage is inadequate, and one where a post-cutoff edit invalidates the fingerprint. Run focused conversion/evaluation suites before any UI work.

**Gate 3:** Synthetic/disposable fixtures must prove leakage prevention, equivalent-input paired scoring, negative/inconclusive decisions, fingerprint invalidation and the pre-registered uncertainty rule. They do not prove benefit for a person. The dashboard may offer explicit Start after Gates 1–3; each user-started run must pass the paired held-out rule against defaults and its expected incumbent before that candidate can be offered for activation.

## Pre-implementation review

Independent SPEC and Ponytail plan reviews found and resolved three blocking sequencing/data issues: the held-out benefit decision now happens per user-started run, ordinary Save/Update require a real history mutation version before chunk consistency can be claimed, and ambiguous earlier observations exclude a card's later primary-cohort predictions rather than being silently skipped. Ponytail also found a WXT lockfile/local-install mismatch; reproducible packaged proof now requires `rtk npm ci` and a recorded installed version. The approved master design already establishes the conditional pilot and defaults-retained result.
