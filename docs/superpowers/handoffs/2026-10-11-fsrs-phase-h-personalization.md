# FSRS Phase H: Local Personalization Feasibility Handoff

**Decision:** Retain the current/default scheduler weights. The official local binding started and trained in a disposable packaged Chrome extension, but the reviewed [Phase H plan](../plans/2026-10-11-fsrs-phase-h-personalization.md) failed Gate 1 on model parity and ordinary package installation. Cancellation remains unproven because the disposable probe's error path was defective. No training, activation, worker, optimizer dependency, permission, migration, backup-format, sync, or product UI change remains in the branch. No real user data was read or trained.

Phase H is the final **evaluation** phase of the approved [A–H roadmap](../plans/2026-10-03-fsrs-remediation.md). Its acceptance allowed a documented defaults-retained result. This handoff does not claim that trained weights cannot ever be useful; it records why this binding/release and current authorized build are not ready for the planned local pilot.

## Baseline and method

The branch `codex/fsrs-phase-h-personalization` started from `origin/main` at Phase G merge `ef14c1a5` (PR #209). The older Phase E worktree was not used. `rtk npm ci` restored Node 24.20.0/npm 11.19.0 lockfile dependencies, including WXT 0.21.3 and `ts-fsrs` 5.4.0. The clean pre-probe `rtk npm run check` passed database check, typecheck, lint, and 3,844 tests, with 10 existing/opt-in skips across 251 files.

Context7 resolved the official FSRS documentation. The separate public-beta `@open-spaced-repetition/binding` 0.5.0 uses fsrs-rs 6.5.0; CogniPace profiles target `ts-fsrs` 5.4.0 / FSRS-6.0. The [package audit](../evidence/fsrs-phase-h/official-package-audit.md) records exact published artifacts, MIT licenses, hashes and API requirements. The binding takes one `FSRSBindingItem` per observed review with its preceding card history, integer day gaps with first gap zero, and explicit `enableShortTerm: false` for a daily training run. Its browser README recommends cross-origin isolation, but that recommendation alone was not used to change CogniPace's manifest.

A disposable probe temporarily added the exact binding and WASI package, a dashboard worker entry and a Chrome DevTools driver. It used 200 independent, synthetic three-review card histories to create 400 long-term training observations. The driver loaded a production WXT build into a unique temporary Chrome profile, selected CogniPace's own extension worker by manifest name, opened its packaged dashboard and collected only sanitized numbers/errors. The first driver attempt selected a different extension worker and opened a Chrome error page; selecting by manifest name repaired that harness error before the recorded run. The [sanitized packaged report](../evidence/fsrs-phase-h/packaged-chrome-synthetic.json) and preserved [driver](../evidence/fsrs-phase-h/packaged-driver-source.txt), [dashboard probe](../evidence/fsrs-phase-h/dashboard-probe-source.txt), and [parity test](../evidence/fsrs-phase-h/parity-repro-source.txt) are partial probe sources, not a complete build recipe or shipped product source. The temporary dashboard wiring and forced-install lockfile are not preserved. The parity source's relative FSRS import refers to its temporary location under `src/lib/fsrs/optimizer/`.

## What the packaged run proved

Chrome for Testing 151.0.7922.47 loaded build SHA-256 `ab2bd768ca1180d6254c6c1af5cb1a548470e4cdc2277a78fec7ea859fc8055f` with the existing manifest permissions and `script-src 'self' 'wasm-unsafe-eval'; object-src 'self';` CSP. `crossOriginIsolated` was `false`. The emitted WASM asset was 598,176 bytes and worker JavaScript 191,014 bytes. Official `initOptimizer({ wasm, worker })` started in the dashboard in about 7.8 ms, spawned five workers, and `computeParameters` with `enableShortTerm: false` returned 21 trained weights from 400 synthetic observations. The recorded first completed run took 34.5 ms; two further completed runs took 16.4 and 18.9 ms. Worker targets returned to zero after each completed run. One progress callback sample was observed with a 1 ms poll interval. These timings are for the small synthetic fixture on this browser/device/build, not a training budget or installed-extension capacity promise.

The driver observed dashboard heap at selected points (about 16.7 MB before and 16.7 MB after the recorded first run; later samples varied). This is **not** a continuous peak, does not include service-worker heap, and does not account for larger history transfer or evaluation copies. It observed two timer ticks during the first short training operation; that is a limited responsiveness sample, not proof of a long workload. No real Chrome history snapshot was transferred. G's packaged 5,000-review fixture had only 709,532 local-storage bytes free, its 50,000-review restore hit the runtime message-size limit, and its one-card/10,000-event restore returned persistence-pending with tracked durable keys unchanged. H did not extrapolate those observations or run a larger training history through one message.

## Gate 1 failures

1. **Same-day model semantics.** The trained 21-weight vector was finite and round-tripped through CogniPace's exact scheduler profile codec without normalization. The initial and four-day synthetic state tests passed. An independent read-only check and a deliberately failing focused regression then compared a reviewed card at stability 45, difficulty 8.5, elapsed day 0, rating Again: binding 0.5.0 `FSRSBinding.nextStates` kept stability at **45**, while CogniPace's daily `ts-fsrs` path returned **2.25843238**. At elapsed day 1, both returned about 2.271835 (the largest observed positive-day state difference in the independent sample was 0.00026787). A real `ts-fsrs next()` Good then same-time Again sequence also reduced stability, while the binding retained it. The binding's exposed `nextStates` API has no daily-mode argument. This is a material same-day inference mismatch, not f32 rounding. It means binding predictions/evaluation cannot stand in for CogniPace's authoritative scheduler on genuine same-day lapses. It does **not** by itself prove a trained vector could never improve future scheduling; that would require a separate authoritative held-out evaluation and explicit treatment of same-day data. Under this plan's required full semantic-parity gate, activation cannot proceed.
2. **Cancellation unproven.** The disposable driver sent a cancellation request during a longer configured run, but observed zero live worker targets immediately beforehand. The `workersAtCancelRequest: 5` value counted previously created Worker objects in a Set, not confirmed live workers. The driver observed no resolved result within 10 seconds and an `Uncaught (in promise)` exception. Independent review found two harness faults: the dashboard probe's `catch` references `cardCount` outside its scope, and the driver attaches `.then` without `.catch` to the run. A binding rejection could therefore become a `ReferenceError` and leave the driver's result variable null. This run cannot establish whether cancellation settled, aborted active work or cleaned up workers. A corrected probe would be required before any pilot; this is **not** a proven binding failure. Successful short runs do not meet Gate 1's cancellation proof requirement.
3. **Reproducible install.** Direct `rtk npm install --save-exact` of both official 0.5.0 packages rejected the WASI package with `EBADPLATFORM` (`cpu: wasm32` versus this arm64 host). `--force` allowed the disposable build, but `rtk npm ci` with those direct dependencies again failed `EBADPLATFORM`. The released package path tested here therefore cannot be built by this repository's ordinary clean install without an additional packaging design. The probe did not vendor assets, change CI, or add a platform workaround.

The same-day parity and clean-install failures independently block the reviewed Gate 1; cancellation proof is also absent. After recording evidence, the agent removed the temporary source and dependency changes; clean `rtk npm ci`, `rtk npm run build`, and `rtk git diff --check` passed again. The active scheduler and all persisted data remain as before H.

## Downstream work and product effect

Tasks 2–5 of the Phase H plan were **not implemented** after Gate 1 failed. There is no canonical training-history export, fingerprint, day-gap conversion, user-started UI, chronological held-out comparison, candidate storage, or activation/reversion in the product. No personal-benefit claim was made from synthetic data. Ordinary per-card FSRS stability/difficulty adaptation continues with the existing default weights, saved retention, active daily policy and original-profile Update behavior. A later attempt would need a new reviewed plan that resolves same-day semantics through the authoritative scheduler, demonstrates reliable cancellation and a clean package path, then meets the history/evaluation/activation gates without expanding permissions or sync.
